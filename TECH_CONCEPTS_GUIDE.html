SỔ TAY KỸ THUẬT: TECH SPEC, ADR, NFR & RISK REGISTER

Tài liệu tổng hợp ngắn gọn các khái niệm kiến trúc phần mềm cốt lõi, kèm ví dụ thực tế trong dự án DrinkBot MLOps.

1. TECH SPEC (Technical Specification - Đặc tả kỹ thuật)

Bản chất: Là bản vẽ thiết kế kỹ thuật do Software Engineer / Tech Lead viết trước khi code, giải quyết câu hỏi: "Làm tính năng này như thế nào về mặt kỹ thuật?"

Cấu trúc chuẩn của một Tech Spec:

  1. Overview & Goals: Bối cảnh bài toán, mục tiêu và những gì không nằm trong phạm vi (Non-goals).
  2. System Architecture: Sơ đồ luồng xử lý (Data flow), các service tham gia.
  3. Data Schema: Cấu trúc bảng Database, kiểu dữ liệu, quan hệ khóa ngoại (Foreign Keys).
  4. API Contracts: Chi tiết các endpoint (URL, Method, Request/Response payload).
  5. Security & Safety: Xác thực, phân quyền, các lớp bảo vệ dữ liệu.
  6. Rollout & Monitoring: Cách deploy, metrics cần đo, phương án rollback khi lỗi.
💡 Ví dụ thực tế trong DrinkBot:
Đề bài yêu cầu: "Chatbot nhận diện dị ứng và không gợi ý món độc hại".
→ Tech Spec sẽ mô tả cụ thể:
  • Viết hàm Python filter_allergens() mở rộng từ khóa dị nguyên (ví dụ: dairy → milk, cream, yogurt, whey).
  • Lọc bỏ các món chứa dị nguyên ngay trong backend trước khi đưa vào danh sách context cho LLM.
  • Khi đặt hàng, hàm order kiểm tra lại một lần nữa bằng code Python trước khi tạo bản ghi vào DB.

2. ADR (Architecture Decision Record - Bản ghi quyết định kiến trúc)

Bản chất: Là văn bản ghi lại lý do tại sao chọn giải pháp này mà bỏ giải pháp khác, để tránh việc sau vài tháng trong team không ai nhớ vì sao lại làm như vậy.

Mẫu một tài liệu ADR tiêu chuẩn:

Thành phần Ý nghĩa
Title (Tiêu đề) Định danh ngắn gọn, thường đánh số: ADR-01: ...
Status (Trạng thái) Proposed (Đề xuất), Accepted (Đã duyệt), Deprecated (Hết hạn), hoặc Superseded (Bị thay thế).
Context (Bối cảnh) Vấn đề kỹ thuật hoặc bài toán kinh doanh đang phải đối mặt là gì?
Decision (Quyết định) Giải pháp công nghệ được chọn là gì?
Trade-offs (Hệ quả / Đánh đổi) Ưu điểm nhận được là gì? Nhược điểm hoặc gánh nặng kỹ thuật phải chấp nhận là gì?
💡 Ví dụ ADR mẫu của DrinkBot:
ADR-02: Quản lý Prompt động qua Database thay vì Hardcode trong mã nguồn.
  • Context: Trước đây Prompt được viết cứng trong code Python. Mỗi lần sửa prompt hay đổi văn phong phải commit code và redeploy container, gây gián đoạn hệ thống.
  • Decision: Xây dựng bảng PromptVersion trong PostgreSQL, tích hợp hash SHA256 và endpoint POST /api/telemetry/prompts/activate để hot-swap prompt runtime.
  • Consequences:
    • Ưu điểm: Đổi prompt hoặc rollback tức thì trong 1 giây, hỗ trợ A/B testing không downtime.
    • Đánh đổi: Phải thêm logic truy vấn DB hoặc cache in-memory trước mỗi lượt chat.

3. NFR (Non-Functional Requirements - Yêu cầu phi chức năng)

Bản chất: Quy định các tiêu chuẩn về chất lượng và vận hành của hệ thống (chạy nhanh không, an toàn không, chịu tải thế nào), thay vì tính năng (làm được nút gì).

Các nhóm NFR phổ biến & Chỉ số thực tế trong dự án:

Nhóm NFR Tiêu chuẩn đo lường Triển khai thực tế trong DrinkBot
Performance
(Hiệu năng)		 Latency phản hồi, throughput (RPS). Thời gian phản hồi LLM trung bình < 2.5s; API nội bộ < 150ms. Đo lường qua Langfuse Tracing.
Safety & Accuracy
(Độ chính xác)		 Tỷ lệ vi phạm an toàn = 0%. Allergen Guardrail: 100% test case dị ứng phải Pass trong bộ Evals Benchmark trước khi release.
Security
(Bảo mật)		 Xác thực, phân quyền, mã hóa. Xác thực phiên qua JWT token; Validate số điện thoại định dạng VN; Các endpoint quản trị Prompt yêu cầu quyền Admin.
Availability
(Độ sẵn sàng)		 Khả năng chịu lỗi khi bên thứ 3 sập. Tự động fallback sang thuật toán Heuristic ranking nếu OpenAI API timeout hoặc gặp sự cố mạng.
Observability
(Khả năng quan sát)		 Khả năng theo dõi chi phí & hành vi. Ghi nhận đầy đủ: Request ID, Model, Prompt Hash, Input/Output Tokens, Chi phí USD cho từng tin nhắn.

4. RISK REGISTER (Sổ đăng ký & Quản trị rủi ro)

Bản chất: Là bảng thống kê toàn bộ những rủi ro kỹ thuật và vận hành có thể xảy ra trong dự án, kèm mức độ nghiêm trọng và kế hoạch phòng ngừa / xử lý (Mitigation Plan).

Bảng Risk Register thực tế của hệ thống DrinkBot MLOps:

Mã Rủi ro tiềm ẩn (Risk) Xác suất Ảnh hưởng Giải pháp phòng ngừa & Ứng phó (Mitigation)
R-01 LLM bị hallucination gợi ý món chứa chất dị ứng của khách Trung bình Nghiêm trọng Code-level Filter: Không tin tưởng LLM. Python backend chủ động lọc sạch menu trước khi gửi vào LLM prompt.
R-02 Khách vô tình bị trừ tiền hoặc chốt đơn nhầm do AI hiểu sai Trung bình Nghiêm trọng Human-in-the-Loop Gate: Tool order chỉ tạo đơn ở trạng thái Pending. Bắt buộc người dùng bấm xác nhận mới tạo đơn Placed.
R-03 Chi phí OpenAI API vượt ngân sách do bot bị spam hoặc lặp vô tận Cao Trung bình Giới hạn vòng lặp tool calling tối đa 4 lượt (bounded loop); Ghi nhận chi phí realtime qua Langfuse Telemetry.
R-04 Prompt mới cập nhật làm giảm chất lượng hội thoại (Prompt Drift) Trung bình Trung bình Gắn mã băm SHA256 cho mỗi phiên bản; Chạy bộ Centralized Evals Benchmark trước khi bấm nút Activate trên production.
R-05 OpenAI API mất kết nối / nghẽn mạng toàn cầu Thấp Cao Xây dựng fallback sang mô hình cục bộ (Ollama SLM) hoặc rule-based recommender để chatbot không bị crash.

5. BẢNG TỔNG KẾT ĐỂ NHỚ NHANH

Thuật ngữ Ý nghĩa cốt lõi Cách trả lời nhanh khi được hỏi
Tech Spec Bản vẽ kỹ thuật chi tiết của hệ thống. "Tài liệu mô tả chi tiết kiến trúc, DB và API trước khi code."
ADR Bản ghi lý do ra quyết định kỹ thuật. "Ghi lại tại sao nhóm chọn giải pháp này và chấp nhận đánh đổi gì."
NFR Yêu cầu phi chức năng (Chất lượng hệ thống). "Tiêu chuẩn về tốc độ, an toàn, bảo mật và chi phí vận hành."
Risk Register Sổ theo dõi rủi ro và kế hoạch phòng cháy. "Bảng dự báo các sự cố có thể xảy ra và phương án giải quyết cụ thể."
